# CHG-019 — Controlled Suricata detection and Wazuh Dashboard triage

## Objective

Validate one safe, purpose-built network detection end to end through the existing Mini-SOC pipeline:

`SOC-TEST-01 -> SOC-GW-01/Suricata -> EVE JSON -> Wazuh Agent -> Wazuh Manager -> native rule 86601 -> Threat Hunting -> SOC L1 triage`.

This change demonstrates detection engineering and analyst workflow. It does not introduce prevention, attack simulation, or automated response.

## Pre-change baseline

Before activation:

- `suricata`, `wazuh-agent` and `nftables` were active on `SOC-GW-01`.
- Suricata's `default-rule-path` was `/var/lib/suricata/rules`.
- The Suricata-Update managed ruleset was `/var/lib/suricata/rules/suricata.rules`.
- The generated/vendor ruleset was not edited.
- Suricata remained passive on `enp0s8`.
- nftables remained the enforcement boundary.
- CHG-018 had already validated EVE JSON collection by Wazuh Agent ID 002.

## Detection design

A single local rule was isolated in:

`/var/lib/suricata/rules/mini-soc-local.rules`

Rule:

```
alert icmp 10.77.0.10 any -> 10.77.0.1 any (msg:"MINI-SOC Authorized ICMP Detection Test"; itype:8; sid:1000001; rev:1;)
```

Design constraints:

- source is restricted to `SOC-TEST-01` (`10.77.0.10`);
- destination is restricted to the gateway (`10.77.0.1`);
- protocol is ICMP;
- only Echo Request (`itype:8`) matches;
- SID `1000001` is used as a local signature identifier;
- the signature describes the event as an authorized test;
- no exploit payload or adversarial traffic is required.

The local file was `root:root` mode `0644`.

The only Suricata configuration change was adding `mini-soc-local.rules` alongside the existing `suricata.rules` entry. A local backup was retained as:

`/etc/suricata/suricata.yaml.pre-chg019`

## Validation before activation

Before restarting the sensor:

```
suricata -T -c /etc/suricata/suricata.yaml
```

The first interactive invocation appeared not to return promptly and was interrupted. No restart was performed on that incomplete validation.

A bounded verbose validation was then executed. It completed successfully:

- 2 rule files processed;
- 53,039 rules successfully loaded;
- 0 rules failed;
- 53,044 signatures processed;
- configuration successfully loaded;
- exit code 0.

This validation gate prevented activation based on an ambiguous test result.

## Activation

Suricata was restarted only after successful validation.

Post-restart state:

- service active/running;
- systemd `ExecStart` completed with status `0/SUCCESS`;
- no rule-load failure was observed.

Suricata remained in IDS mode. No IPS/NFQUEUE or Active Response was introduced.

## Controlled detection UAT

From `SOC-TEST-01`, exactly one controlled ICMP Echo Request was sent to the gateway:

`10.77.0.10 -> 10.77.0.1`

The request received one reply with 0% packet loss.

Suricata EVE produced a matching alert with:

- `event_type: alert`;
- `in_iface: enp0s8`;
- source `10.77.0.10`;
- destination `10.77.0.1`;
- protocol `ICMP`;
- `icmp_type: 8`;
- signature ID `1000001`;
- signature `MINI-SOC Authorized ICMP Detection Test`;
- severity `3`;
- action `allowed`;
- packet source `wire/pcap`.

The `allowed` action is expected: this change validates detection, while nftables remains the network enforcement control.

## Wazuh end-to-end validation

On `SOC-MGMT-01`, the alert was present in Wazuh alerts.

Wazuh recorded:

- agent ID `002`;
- agent name `SOC-GW-01`;
- decoder `json`;
- source location `/var/log/suricata/eve.json`;
- rule ID `86601`;
- rule level `3`;
- groups `ids, suricata`;
- description `Suricata: Alert - MINI-SOC Authorized ICMP Detection Test`.

This confirms that the existing native Wazuh Suricata rule handled the event. No custom Wazuh decoder or manager rule was required.

## Dashboard / SOC L1 triage

Threat Hunting filtered on `rule.id:86601` displayed the controlled event as a distinct hit from `SOC-GW-01`.

The document detail preserved the relevant analyst context: agent, source, destination, interface, protocol, ICMP type, Suricata SID/signature, action, Wazuh rule, decoder, groups and log source.

Analyst disposition:

**True Positive — Authorized Security Test / Benign**

- Escalation: **No**
- Containment: **No**
- Active Response: **No**
- MITRE ATT&CK mapping: **Not assigned**

ATT&CK is intentionally not forced onto this event. The ICMP request was created as a deterministic validation signal and does not, by itself, represent a defensible adversary technique.

The Threat Hunting result also showed other historical Suricata rule-86601 alerts. They were not treated as duplicates of this controlled signature.

## Post-change regression check

After detection and Dashboard validation:

- `suricata`: active;
- `wazuh-agent`: active;
- `nftables`: active;
- `net.ipv4.ip_forward = 1`;
- nftables FORWARD policy remained `drop`;
- established/related forwarding remained allowed;
- new forwarding remained restricted to `10.77.0.0/24` from `enp0s8` to `enp0s3`;
- root filesystem remained at approximately 24% usage with approximately 14 GiB available.

No enforcement or routing regression was observed.

## Security decisions

This change deliberately:

- uses a benign deterministic signal rather than exploit traffic;
- keeps the custom signature separate from Suricata-Update generated rules;
- validates configuration before activation;
- does not modify Wazuh manager rules because native handling is sufficient;
- does not enable IPS/NFQUEUE or Active Response;
- does not force an ATT&CK mapping for portfolio appearance;
- does not commit raw EVE telemetry, PCAP, credentials or private evidence.

The test signature is a detection harness, not a claim that ICMP is inherently malicious.

## Rollback

Targeted rollback:

1. Remove `mini-soc-local.rules` from the `rule-files` list, or restore `/etc/suricata/suricata.yaml.pre-chg019`.
2. Validate with `suricata -T` and require exit code 0.
3. Restart Suricata.
4. Remove `/var/lib/suricata/rules/mini-soc-local.rules` if the harness is no longer required.
5. Revalidate Suricata, Wazuh Agent, nftables, forwarding and the existing telemetry path.

No database, Wazuh manager rule, network-interface, route or firewall rollback is required.

## Out of scope

- IPS/NFQUEUE;
- Active Response;
- YARA/VirusTotal;
- multiple network-detection scenarios;
- enrollment-service hardening;
- unrelated gateway INPUT/OUTPUT hardening;
- README and architecture-diagram refresh.

## Portfolio evidence

CHG-019 demonstrates a complete detection lifecycle: scoped detection design, isolation from vendor-managed rules, pre-activation validation, controlled test generation, passive network detection, centralized telemetry, native SIEM rule processing, Dashboard visibility, analyst triage, evidence-based disposition, separation of detection from enforcement, regression validation, rollback and change governance.
