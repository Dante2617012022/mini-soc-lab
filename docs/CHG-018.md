# CHG-018 — Integrate Suricata EVE telemetry into Wazuh

## Objective

Integrate the existing Suricata EVE JSON source on `SOC-GW-01` with the Wazuh central platform while preserving the passive NIDS design, nftables enforcement boundary, existing endpoint telemetry, and minimum-data posture.

## Scope and trust boundary

- Producer/sensor: `SOC-GW-01`, Suricata on `enp0s8`.
- Local source: `/var/log/suricata/eve.json`.
- Collector: Wazuh Agent `4.14.8-1` on `SOC-GW-01`.
- Manager: existing Wazuh Manager `4.14.8`.
- Transport: existing agent channel on TCP/1514; enrollment used the existing TCP/1515 service.
- No new NIC, bridge, manager API/dashboard exposure, syslog relay, or firewall exception was introduced.
- Suricata remains passive; nftables remains the enforcement control.
- Active Response, IPS/NFQUEUE, custom Suricata signatures, YARA/VirusTotal and unrelated hardening remain out of scope.

## Pre-change baseline

Before the change:

- Suricata was active/enabled and producing EVE JSON.
- `eve.json` used regular-file output; raw PCAP/payload collection was not enabled for this integration.
- The gateway retained approximately 14 GiB free on its root filesystem.
- `SOC-GW-01` could reach the manager's existing TCP/1514 and TCP/1515 listeners through its current upstream path; therefore no additional interface or route was required.
- `SOC-ENDPOINT-01` was confirmed `Active` before introducing the new agent.
- No Wazuh package or Wazuh APT source existed on the gateway.

## Implementation

A powered-off VirtualBox snapshot named `SURICATA-NIDS-READY` was created before installing Wazuh, providing an explicit rollback boundary for the validated Suricata/nftables state.

The official Wazuh APT source was added with its signing key. Package policy was checked before installation and showed `4.14.8-1` as the candidate. The exact manager-compatible agent version was installed:

- package: `wazuh-agent`
- version: `4.14.8-1`
- architecture: `amd64`
- agent name: `SOC-GW-01`

The package was placed on APT hold to avoid an unintended agent-only upgrade.

Enrollment was performed against the existing manager enrollment service. A valid key was received and the manager registered `SOC-GW-01` as agent ID 002. The manager accepted enrollment without an authentication password; this is recorded as a trust-boundary observation for a separate hardening decision rather than changed opportunistically in this integration.

The agent was enabled only after central registration was verified. Both `SOC-ENDPOINT-01` and `SOC-GW-01` were then confirmed `Active`.

## EVE collection

The existing EVE file was `root:root` mode `0644`, so no permission relaxation or group change was required.

A backup of the agent configuration was retained locally as:

`/var/ossec/etc/ossec.conf.pre-chg018`

The minimum collector configuration added to the gateway agent was:

```xml
<localfile>
  <log_format>json</log_format>
  <location>/var/log/suricata/eve.json</location>
</localfile>
```

`wazuh-logcollector -t` completed without error before the service restart. After restart, the agent log explicitly recorded:

`Analyzing file: '/var/log/suricata/eve.json'.`

No additional telemetry source, raw PCAP, payload collection, remote syslog service or new listener was introduced.

## Wazuh ruleset behavior

Read-only inspection of the manager's packaged `0475-suricata_rules.xml` confirmed native Suricata JSON handling:

- rule 86600: base Suricata JSON message, level 0;
- rule 86601: `event_type=alert`, level 3;
- rule 86602: HTTP, level 0;
- rule 86603: DNS, level 0;
- rule 86604: TLS, level 0.

This distinction is important: collection of EVE telemetry does not imply that every network event becomes a SOC alert. The deployed ET Open ruleset did not contain a suitable benign purpose-built IDS test signature. CHG-018 therefore does not generate exploit traffic or add a custom signature merely to force a Dashboard alert. Controlled Suricata alert generation and analyst triage are intentionally separated into the next detection-engineering change.

## Controlled UAT

A controlled test workload remained isolated behind the gateway.

- `SOC-TEST-01 -> 1.1.1.1`: 3/3 ICMP replies, 0% loss.
- Suricata continued observing the internal segment on `enp0s8`.
- Fresh EVE evidence included an SSH application event for the controlled management session between the gateway and `SOC-TEST-01`.
- Wazuh Logcollector was confirmed reading the EVE source.
- The existing endpoint remained `Active` throughout the change.

The manager's archive file was not used as proof of generic level-0 event visibility because archive logging was not established as enabled. This avoids enabling broad archival or changing central logging policy solely to manufacture evidence.

## Resource and retention check

After integration:

- root filesystem: 19 GiB total, approximately 4.1 GiB used, 14 GiB available (24%);
- memory: 1.9 GiB total, approximately 899 MiB used, approximately 1.0 GiB available;
- swap: 1.1 GiB total, 0 used;
- Suricata log directory: approximately 23 MiB at the observed checkpoint.

The Debian Suricata logrotate policy covers `*.log` and `*.json`, retains 14 rotations, compresses rotated logs and signals Suricata after rotation. Existing `.1.gz` files demonstrated that rotation was operating. No retention change was justified.

## Reboot and persistence UAT

After a controlled gateway reboot:

- `suricata`, `wazuh-agent` and `nftables` were all active and enabled;
- `enp0s8` retained `10.77.0.1/24`;
- the only default route remained through `enp0s3`;
- `net.ipv4.ip_forward = 1`;
- nftables FORWARD policy remained default deny;
- established/related return traffic remained allowed;
- new forwarding remained scoped to `10.77.0.0/24` from `enp0s8` to `enp0s3`;
- masquerade remained scoped to the same lab subnet;
- Wazuh Logcollector automatically reopened `eve.json`;
- centrally, both `SOC-ENDPOINT-01` and `SOC-GW-01` were `Active`.

No regression to the existing endpoint path or gateway enforcement boundary was observed.

## Security decisions

This change deliberately avoids adding a third gateway NIC or bridged home-LAN attachment because the existing upstream path already reaches the manager. It also avoids relaxing EVE permissions, exposing the Wazuh API/dashboard, enabling generic archive logging, adding custom IDS signatures, or coupling telemetry integration with automated response.

The passwordless enrollment behavior on TCP/1515 is a recorded hardening consideration. It is not silently changed here because enrollment policy affects the wider Wazuh trust boundary and deserves its own reviewed change.

## Rollback

Preferred full rollback:

1. Power off `SOC-GW-01`.
2. Restore the `SURICATA-NIDS-READY` snapshot.
3. Validate Suricata, nftables, routing and test-segment connectivity.

Targeted Wazuh rollback:

1. Stop/disable `wazuh-agent`.
2. Restore `/var/ossec/etc/ossec.conf.pre-chg018` if only EVE collection must be removed.
3. Remove the gateway agent registration centrally if the enrollment itself is being reverted.
4. Remove/purge the gateway agent and Wazuh package source only if full package rollback is required.
5. Revalidate the existing `SOC-ENDPOINT-01` path.

Enrollment keys, secrets, raw EVE records and PCAP are not committed to this public repository.
