# CHG-017 — Suricata passive NIDS on SOC-GW-01

## Objective

Deploy and validate Suricata on `SOC-GW-01` as a passive network IDS observing the isolated `SOC-LAB-INTERNAL` segment, without converting the gateway into an IPS and without changing the existing Wazuh endpoint/manager path.

## Scope and security boundaries

- Sensor host: `SOC-GW-01`.
- Capture interface: `enp0s8`, connected to `SOC-LAB-INTERNAL`.
- Test workload: `SOC-TEST-01`.
- Suricata remains passive IDS only.
- Existing nftables forwarding/NAT policy remains the enforcement point.
- No Wazuh Agent enrollment or EVE-to-Wazuh integration is included.
- No Active Response, YARA/VirusTotal, custom attack simulation, packet capture retention, or unrelated gateway hardening is included.

## Pre-change baseline

Before installation, the gateway retained the CHG-015 network design:

- `enp0s3`: upstream VirtualBox NAT path.
- `enp0s8`: `SOC-LAB-INTERNAL`, gateway address `10.77.0.1/24`.
- Default route through `enp0s3`.
- IPv4 forwarding enabled.
- nftables FORWARD policy default deny.
- Established/related return traffic allowed.
- Only the isolated `10.77.0.0/24` segment is allowed to initiate forwarding through `enp0s3`.
- Scoped masquerade is applied to that segment.

The root filesystem had approximately 14 GiB available before installation.

## Implementation

Suricata was installed from the existing Debian package authority:

- Suricata `7.0.10`.
- `suricata-update` installed as a Debian dependency/tool.
- No additional package repository was introduced.

The packaged service initially failed because the default AF_PACKET configuration referenced `eth0`, while the required internal interface is `enp0s8`.

A backup was created:

`/etc/suricata/suricata.yaml.pre-chg017`

The minimum configuration change was then applied:

`af-packet -> interface: enp0s8`

No nftables rules were changed and Suricata was not placed inline.

Configuration validation with `suricata -T` succeeded. The initial warning about a missing rules file was addressed using `suricata-update`.

## Availability incident discovered during reboot UAT

The first post-installation reboot exposed a dataplane availability defect on the internal virtual NIC.

Observed symptoms:

- `enp0s8` remained administratively `UP,LOWER_UP`.
- The `10.77.0.0/24` route remained present.
- The interface received packets but initially transmitted zero packets.
- Kernel logs repeatedly reported `e1000 ... enp0s8: Detected Tx Unit Hang`.
- `SOC-GW-01` could not reach `SOC-TEST-01`.

A logical down/up cycle temporarily restored transmission, but new `Tx Unit Hang` messages continued. This demonstrated that the issue was recurrent rather than a one-off routing or firewall failure.

The fault was isolated to the VirtualBox Intel PRO/1000 (e1000) emulation used by NIC2. The minimum hypervisor remediation was to change only NIC2 to the paravirtualized `virtio-net` adapter while preserving:

- Internal Network `SOC-LAB-INTERNAL`.
- Existing MAC address.
- VirtualBox cable-connected state.
- Promiscuous policy.
- NIC1/upstream configuration.
- Guest network configuration.
- Suricata interface configuration.

After boot, Debian retained the interface name `enp0s8` and loaded it through `virtio_net`. No NetworkManager or Suricata reconfiguration was required.

## Final UAT

After the virtio-net remediation:

- `enp0s8` was `UP,LOWER_UP`.
- No new e1000 `Tx Unit Hang` condition was present.
- Gateway-to-test connectivity succeeded with 0% packet loss.
- Suricata was active and opened `enp0s8`.
- AF_PACKET capture threads were created and the engine started.
- `SOC-TEST-01 -> 1.1.1.1` succeeded 4/4 with 0% packet loss.
- EVE JSON contained traffic from `10.77.0.10` observed on `enp0s8`.
- nftables remained the forwarding enforcement control.
- IPv4 forwarding and the isolated routed path remained functional.

The AF_PACKET log also recommends tpacket-v3 for non-inline operation. This is treated as a non-blocking optimization candidate and is not changed opportunistically in CHG-017.

## Risk treatment

This change deliberately separates detection from prevention. Suricata observes the internal routed segment but does not make blocking decisions. This limits the blast radius of sensor failure and preserves nftables as the explicit network enforcement control.

The reboot UAT was important: service health alone would not have detected the e1000 transmit failure. The resulting virtio-net remediation improves availability while avoiding changes to higher-layer security policy.

## Rollback

Suricata configuration rollback:

1. Stop Suricata if required.
2. Restore `/etc/suricata/suricata.yaml.pre-chg017`.
3. Validate with `suricata -T -c /etc/suricata/suricata.yaml`.
4. Restart or disable Suricata depending on rollback scope.

Hypervisor rollback:

1. Power off `SOC-GW-01`.
2. Restore NIC2's prior Intel PRO/1000 adapter type while preserving the internal-network settings.
3. Boot and validate the internal interface and routing.

The prior e1000 configuration is not the preferred steady state because reboot UAT reproduced a transmit-hang condition.

Full gateway rollback remains available through the previously established baseline snapshot/change controls.
