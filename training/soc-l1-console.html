Mini-SOC · entrenamiento operativo

Consola de práctica SOC L1

Casos basados únicamente en controles y detecciones ya validados del laboratorio. Cada card separa generación del evento, alerta esperada, triage, evidencia, decisión y cierre para practicar como si estuvieras atendiendo una cola SOC.

Uso autorizado: ejecutá estos tests sólo dentro de tu Mini-SOC. La interfaz no ejecuta comandos, no contiene credenciales y no modifica Wazuh, Suricata, nftables ni las VMs.
Nivel 1TEST-001Endpoint

Fallo de autenticación SSH

Entrená triage de un único fallo de autenticación sin confundirlo con brute force o compromiso.

sshd → journald → Wazuh Agent → Manager → Rule 5760 → Threat Hunting
1. Generar el evento

PC principal · Windows PowerShell

  1. Confirmá primero que SOC-ENDPOINT-01 aparece Active en Wazuh.
  2. Ejecutá una conexión SSH al port-forward local:
ssh -p 2222 socops@127.0.0.1
  1. Ingresá una sola contraseña incorrecta.
  2. Cancelá con Ctrl+C. No hagas múltiples intentos.
2. Qué deberías ver
  • Wazuh Rule 5760, level 5.
  • Descripción: sshd: authentication failed.
  • Agente: 001 / SOC-ENDPOINT-01.
  • Puede aparecer luego Rule 5762 por reset de conexión.
  • MITRE de Wazuh: T1110.001 y T1021.004; es contexto, no prueba de ataque.
3. Triage SOC L1
  1. Ubicá el evento por timestamp, agente y rule.id:5760.
  2. Verificá usuario, origen y cantidad de intentos en la ventana cercana.
  3. Buscá eventos inmediatamente anteriores/posteriores, incluida Rule 5762.
  4. Si necesitás corroboración local, revisá el journal del endpoint:
journalctl -u ssh --since "-10 min" --no-pager | tail -n 80
  1. Preguntate: ¿es un único fallo o una secuencia? ¿hubo acceso exitoso después? ¿el usuario y host son esperados?
4. Decisión y cierre

Ejercicio validado: True Positive — Authorized Security Test / Benign. Sin contención.

No concluir: un único fallo no demuestra brute force, lateral movement ni cuenta comprometida.

Nivel 1TEST-002FIM

Modificación de archivo monitorizado

Practicá integridad, correlación temporal y diferencia entre “cambio real” e “intención maliciosa”.

archivo → Wazuh FIM/syscheck → Rule 550 → Threat Hunting
1. Generar el evento

El path validado es /opt/mini-soc/fim-test/controlled.conf. No uses directorios productivos.

  1. Confirmá Agent 001 activo y FIM realtime habilitado para /opt/mini-soc/fim-test.
  2. En SOC-ENDPOINT-01, usá una sesión root autorizada. Si entrás con su -, recordá que también generarás telemetría de privilegios.
  3. Modificá una sola vez el archivo controlado:
printf 'mini-soc-fim-training-001\n' > /opt/mini-soc/fim-test/controlled.conf
  1. No reinicies Wazuh después del cambio; la prueba busca validar realtime.
2. Qué deberías ver
  • Wazuh Rule 550, level 7.
  • Integrity checksum changed.
  • mode: realtime y event: modified.
  • Cambios de integridad: mtime y hashes MD5/SHA1/SHA256.
  • Agente: 001 / SOC-ENDPOINT-01.
3. Triage SOC L1
  1. Validá path exacto y tipo de evento.
  2. Revisá qué atributos cambiaron y los valores de integridad antes/después disponibles en Wazuh.
  3. Buscá eventos de identidad/privilegios alrededor del timestamp para entender quién pudo modificarlo.
  4. Corroborá el estado actual del archivo sólo si aporta contexto:
stat /opt/mini-soc/fim-test/controlled.conf
sha256sum /opt/mini-soc/fim-test/controlled.conf
  1. Determiná si el cambio estaba autorizado antes de decidir escalamiento.
4. Decisión y cierre

Ejercicio validado: True Positive — Authorized Security Test / Benign.

No concluir: un checksum cambiado confirma modificación, no malware ni compromiso por sí solo.

Nivel 2TEST-003Identidad

Sesión privilegiada con su -

Entrená triage de una transición real a root sin asumir que toda actividad privilegiada es un incidente.

socops → su - → PAM → Wazuh Rule 5501 / 5502
1. Generar el evento
  1. Entrá a SOC-ENDPOINT-01 como socops.
  2. Ejecutá:
su -
  1. Autenticate correctamente como root.
  2. Como verificación inocua podés ejecutar whoami.
  3. Salí inmediatamente con exit; no realices cambios privilegiados.
2. Qué deberías ver
  • Rule 5501, level 3: PAM: Login session opened.
  • Program: su; source user socops; target user root; source UID 1000.
  • Rule 5502 registra el cierre de sesión.
  • Wazuh aporta contexto ATT&CK T1078 — Valid Accounts.
3. Triage SOC L1
  1. Confirmá identidad origen y destino: socops → root.
  2. Correlacioná apertura y cierre de sesión por timestamp.
  3. Buscá cambios, comandos o alertas relevantes ocurridos dentro de esa ventana.
  4. Si necesitás corroboración local:
journalctl --since "-10 min" _COMM=su --no-pager
  1. Validá si la actividad estaba autorizada. ATT&CK no determina intención.
4. Decisión y cierre

Ejercicio validado: True Positive — Authorized Administrative Activity / Benign.

Separá siempre: verdad del evento, verdad de la detección, contexto ATT&CK y conclusión del incidente.

Nivel 2TEST-004Network IDS

Anomalía UDP controlada

Practicá una detección de red end-to-end sin contención automática y sin convertir una anomalía en “DDoS”.

TEST → GW/Suricata SID 1000002 → EVE JSON → Wazuh Rule 86601
1. Generar el evento
  1. Desde Windows PowerShell entrá al gateway:
ssh -p 2223 socops@127.0.0.1
  1. Desde SOC-GW-01 entrá al workload:
ssh socops@10.77.0.10
  1. Ejecutá primero el baseline negativo:
hping3 --udp -p 65000 -c 5 -i 1 10.77.0.1
  1. Después ejecutá el caso positivo acotado:
hping3 --udp -p 65000 -c 30 -i u20000 10.77.0.1

No uses --flood. Este caso está diseñado como anomalía de tasa limitada, no como prueba DoS/DDoS.

2. Qué deberías ver
  • Suricata SID 1000002: MINI-SOC Controlled UDP Rate Anomaly.
  • Origen 10.77.0.10 → destino 10.77.0.1:65000/UDP.
  • Acción Suricata: allowed.
  • Wazuh Rule 86601, level 3, desde /var/log/suricata/eve.json.
  • No debe aparecer un nuevo SID 1000001 ni Active Response.
3. Triage SOC L1
  1. En Threat Hunting buscá data.alert.signature_id:1000002 o Rule 86601 y acotá el tiempo.
  2. Validá origen, destino, puerto, protocolo, agente SOC-GW-01 y signature.
  3. Revisá eventos cercanos para descartar que el flujo haya activado SID 1000001 o contención.
  4. Si querés corroborar el evento directamente en GW:
grep -F '"signature_id":1000002' /var/log/suricata/eve.json | tail -n 1
  1. Evaluá impacto real. La condición de tasa por sí sola no prueba ataque ni degradación de servicio.
4. Decisión y cierre

Ejercicio validado: True Positive — Authorized Security Test / Benign.

Escalación: no. Contención: no. Active Response: no. ATT&CK: no forzado sin contexto adversario.

Nivel 3TEST-005Response

Active Response con rollback

Practicá la diferencia entre detectar y contener: aquí sí existe una respuesta automática acotada.

SID 1000001 → Wazuh 86601 → local 100021 → Python → nftables → timeout 60 s
1. Generar el evento
  1. Desde SOC-TEST-01, comprobá baseline de salida:
ping -c 3 -W 2 1.1.1.1
  1. Generá un solo Echo Request al gateway:
ping -c 1 10.77.0.1
  1. Esperá aproximadamente 5 segundos.
  2. Volvé a probar conectividad de salida:
ping -c 3 -W 2 1.1.1.1
  1. Esperá ~60 segundos y repetí el ping de salida para comprobar recuperación.
2. Qué deberías ver
  • Suricata SID 1000001 por ICMP autorizado.
  • Wazuh Rule nativa 86601.
  • Regla local Wazuh 100021 como trigger específico.
  • Active Response local en SOC-GW-01.
  • nftables bloquea temporalmente sólo 10.77.0.10.
  • Después del timeout de 60 s se ejecuta DELETE y vuelve la conectividad.
3. Triage / validación SOC L1
  1. Confirmá que el evento corresponde a SID 1000001, no a 1000002.
  2. Revisá que el origen sea exactamente 10.77.0.10.
  3. En el gateway, verificá el estado runtime de la tabla:
sudo nft list table inet mini_soc_ar
  1. Durante el bloqueo, el set blocked_ipv4 debe contener sólo 10.77.0.10.
  2. Después de ~60 s, verificá que el set quede vacío y que TEST recupere conectividad.
  3. Confirmá salud final:
systemctl is-active wazuh-agent suricata nftables
sysctl net.ipv4.ip_forward
4. Decisión y cierre

Ejercicio validado: True Positive — Authorized Security Test / Benign. La contención automática fue intencional.

Control de seguridad: la respuesta está limitada por regla específica, allowlist exacta, ejecución local, tabla nftables runtime y timeout. No modifica /etc/nftables.conf.

Fuente de verdad: docs/detections/SOC-DET-001..004, docs/CHG-019.md, docs/CHG-021.md y docs/CHG-025.md. Esta consola es material de entrenamiento; si una salida real contradice la card, investigá la diferencia antes de forzar una conclusión.
