Mini-SOC · entrenamiento operativo

Consola de práctica SOC L1

Casos basados únicamente en controles y detecciones ya validados del laboratorio. Cada card separa generación del evento, alerta esperada, triage, evidencia, decisión y cierre para practicar como si estuvieras atendiendo una cola SOC.

Uso autorizado: ejecutá estos tests sólo dentro de tu Mini-SOC. La interfaz no ejecuta comandos, no contiene credenciales y no modifica Wazuh, Suricata, nftables ni las VMs.
1 · DetectarUbicá la alerta por tiempo, agente, regla y fuente de datos.
2 · ValidarConfirmá que el evento ocurrió y que la telemetría es confiable.
3 · ContextualizarRevisá usuario, IP, host, eventos cercanos, autorización e impacto.
4 · DecidirCerrá, monitoreá o escalá con evidencia. No respondas por reflejo.
Nivel 1TEST-001Endpoint

Fallo de autenticación SSH

Entrená triage de un único fallo de autenticación sin confundirlo con brute force o compromiso.

sshd → journald → Wazuh Agent → Manager → Rule 5760 → Threat Hunting
0. Objetivo, alcance y precondiciones

Qué entrenás: distinguir un fallo real de autenticación de una conclusión exagerada como “brute force” o “cuenta comprometida”.

  • SOC-ENDPOINT-01 encendido y Agent 001 en estado Active.
  • Telemetría SSH recolectada desde journald.
  • Ventana horaria anotada antes de generar el evento.
  • Una sola prueba autorizada; no repetir credenciales.

Éxito técnico: evento visible en endpoint y alerta Rule 5760 en Wazuh. Éxito analítico: no inferir intención sin contexto.

1. Generar el evento

PC principal · Windows PowerShell

  1. Confirmá primero que SOC-ENDPOINT-01 aparece Active en Wazuh.
  2. Ejecutá una conexión SSH al port-forward local:
ssh -p 2222 socops@127.0.0.1
  1. Ingresá una sola contraseña incorrecta.
  2. Cancelá con Ctrl+C. No hagas múltiples intentos.
2. Localizar la alerta y qué deberías ver

Wazuh Dashboard · Threat Hunting

  1. Abrí Threat Hunting y elegí una ventana corta que cubra la hora de la prueba.
  2. Filtrá por rule.id:5760.
  3. Confirmá que agent.name sea SOC-ENDPOINT-01.
  4. Abrí el documento y anotá timestamp, usuario, origen disponible, descripción y campos de regla.
  • Wazuh Rule 5760, level 5.
  • Descripción: sshd: authentication failed.
  • Agente: 001 / SOC-ENDPOINT-01.
  • Puede aparecer luego Rule 5762 por reset de conexión.
  • MITRE de Wazuh: T1110.001 y T1021.004; es contexto, no prueba de ataque.
3. Triage SOC L1
  1. Ubicá el evento por timestamp, agente y rule.id:5760.
  2. Verificá usuario, origen y cantidad de intentos en la ventana cercana.
  3. Buscá eventos inmediatamente anteriores/posteriores, incluida Rule 5762.
  4. Si necesitás corroboración local, revisá el journal del endpoint:
journalctl -u ssh --since "-10 min" --no-pager | tail -n 80
  1. Preguntate: ¿es un único fallo o una secuencia? ¿hubo acceso exitoso después? ¿el usuario y host son esperados?
  2. Si ves múltiples fallos, ampliá la ventana y contá eventos antes de hablar de brute force.
  3. Si aparece un login exitoso cercano, registralo como contexto y evaluá si corresponde escalar.
4. Decisión y cierre

Ejercicio validado: True Positive — Authorized Security Test / Benign. Sin contención.

No concluir: un único fallo no demuestra brute force, lateral movement ni cuenta comprometida.

Escalá si

  • hay repetición significativa o múltiples usuarios/hosts;
  • aparece un acceso exitoso sospechoso cercano;
  • el origen no es esperado o no existe autorización;
  • hay otras alertas correlacionadas que eleven el riesgo.

Registro mínimo: hora · agente · usuario · origen · rule 5760 · cantidad observada · eventos relacionados · disposición · acción.

Cierre ejemplo: “TP benigno. Un único fallo SSH autorizado, sin evidencia de acceso exitoso o actividad posterior. Sin contención; monitoreo normal.”

5. Si la alerta o el resultado no aparece
  • Agent 001 debe figurar Active.
  • Confirmá que el fallo existe en journald antes de culpar a Wazuh.
  • Si el evento local existe pero no llega, revisá la salud del agente y la conectividad de telemetría.

Regla de operación: no “arregles” varias capas a la vez. Aislá el punto donde se corta el flujo y hacé el cambio mínimo.

Nivel 1TEST-002FIM

Modificación de archivo monitorizado

Practicá integridad, correlación temporal y diferencia entre “cambio real” e “intención maliciosa”.

archivo → Wazuh FIM/syscheck → Rule 550 → Threat Hunting
0. Objetivo, alcance y precondiciones

Qué entrenás: confirmar una modificación real, preservar evidencia de integridad y determinar si el cambio estaba autorizado.

  • Agent 001 activo y sesión de telemetría saludable.
  • /opt/mini-soc/fim-test configurado con FIM realtime.
  • Archivo controlado existente antes de modificarlo.
  • No reiniciar Wazuh para “forzar” la alerta.
1. Generar el evento

El path validado es /opt/mini-soc/fim-test/controlled.conf. No uses directorios productivos.

  1. Confirmá Agent 001 activo y FIM realtime habilitado para /opt/mini-soc/fim-test.
  2. En SOC-ENDPOINT-01, usá una sesión root autorizada. Si entrás con su -, recordá que también generarás telemetría de privilegios.
  3. Modificá una sola vez el archivo controlado:
printf 'mini-soc-fim-training-001\n' > /opt/mini-soc/fim-test/controlled.conf
  1. No reinicies Wazuh después del cambio; la prueba busca validar realtime.
2. Localizar la alerta y qué deberías ver

Wazuh Dashboard · Threat Hunting

  1. Acotá la ventana al momento exacto de la modificación.
  2. Filtrá por rule.id:550 y agent.name:SOC-ENDPOINT-01.
  3. Confirmá path, mode: realtime, tipo de evento y atributos de integridad.
  • Wazuh Rule 550, level 7.
  • Integrity checksum changed.
  • mode: realtime y event: modified.
  • Cambios de integridad: mtime y hashes MD5/SHA1/SHA256.
  • Agente: 001 / SOC-ENDPOINT-01.
3. Triage SOC L1
  1. Validá path exacto y tipo de evento.
  2. Revisá qué atributos cambiaron y los valores de integridad antes/después disponibles en Wazuh.
  3. Buscá eventos de identidad/privilegios alrededor del timestamp para entender quién pudo modificarlo.
  4. Corroborá el estado actual del archivo sólo si aporta contexto:
stat /opt/mini-soc/fim-test/controlled.conf
sha256sum /opt/mini-soc/fim-test/controlled.conf
  1. Determiná si el cambio estaba autorizado antes de decidir escalamiento.
4. Decisión y cierre

Ejercicio validado: True Positive — Authorized Security Test / Benign.

No concluir: un checksum cambiado confirma modificación, no malware ni compromiso por sí solo.

Escalá si

  • el path no corresponde al harness autorizado;
  • el cambio afecta configuración sensible o ejecutables;
  • no existe cambio aprobado o dueño identificable;
  • hay eventos de privilegio, autenticación o red correlacionados.

Registro mínimo: timestamp · host · path · evento · hashes/atributos · identidad asociada · autorización · impacto · disposición.

Cierre ejemplo: “TP benigno. Modificación FIM realtime confirmada sobre archivo controlado; cambio autorizado y sin impacto adicional.”

5. Si la alerta o el resultado no aparece
  • Confirmá que el path exacto está bajo FIM realtime.
  • Verificá Agent 001 Active y no repitas cambios hasta entender la ausencia de telemetría.
  • No aceptes como evidencia una prueba hecha mientras el camino endpoint→manager estaba caído.

Regla de operación: no “arregles” varias capas a la vez. Aislá el punto donde se corta el flujo y hacé el cambio mínimo.

Nivel 2TEST-003Identidad

Sesión privilegiada con su -

Entrená triage de una transición real a root sin asumir que toda actividad privilegiada es un incidente.

socops → su - → PAM → Wazuh Rule 5501 / 5502
0. Objetivo, alcance y precondiciones

Qué entrenás: investigación de identidad y privilegios: quién abrió la sesión, hacia qué cuenta, cuánto duró y qué ocurrió dentro de esa ventana.

  • Inicio desde una shell autenticada de socops.
  • Agent 001 activo.
  • La prueba se limita a abrir y cerrar la sesión root.
  • No realizar cambios privilegiados durante el escenario base.
1. Generar el evento
  1. Entrá a SOC-ENDPOINT-01 como socops.
  2. Ejecutá:
su -
  1. Autenticate correctamente como root.
  2. Como verificación inocua podés ejecutar whoami.
  3. Salí inmediatamente con exit; no realices cambios privilegiados.
2. Localizar la alerta y qué deberías ver

Wazuh Dashboard · Threat Hunting

  1. Filtrá por rule.id:5501 para la apertura.
  2. Confirmá srcuser=socops, destino root, programa su y UID origen.
  3. Buscá Rule 5502 inmediatamente después para cerrar el ciclo.
  • Rule 5501, level 3: PAM: Login session opened.
  • Program: su; source user socops; target user root; source UID 1000.
  • Rule 5502 registra el cierre de sesión.
  • Wazuh aporta contexto ATT&CK T1078 — Valid Accounts.
3. Triage SOC L1
  1. Confirmá identidad origen y destino: socops → root.
  2. Correlacioná apertura y cierre de sesión por timestamp.
  3. Buscá cambios, comandos o alertas relevantes ocurridos dentro de esa ventana.
  4. Si necesitás corroboración local:
journalctl --since "-10 min" _COMM=su --no-pager
  1. Validá si la actividad estaba autorizada. ATT&CK no determina intención.
4. Decisión y cierre

Ejercicio validado: True Positive — Authorized Administrative Activity / Benign.

Separá siempre: verdad del evento, verdad de la detección, contexto ATT&CK y conclusión del incidente.

Escalá si

  • no hay autorización para la elevación;
  • la identidad origen no coincide con el contexto esperado;
  • la sesión queda abierta o aparecen cambios sensibles durante ella;
  • se correlaciona con autenticaciones o FIM sospechosos.

Registro mínimo: apertura · cierre · usuario origen · usuario destino · UID · host · actividad relacionada · autorización · disposición.

5. Si la alerta o el resultado no aparece
  • Confirmá que comenzaste como socops y que la sesión root realmente abrió.
  • Revisá journald/PAM localmente y luego Wazuh.
  • Si falta 5502, comprobá que la sesión se haya cerrado.

Regla de operación: no “arregles” varias capas a la vez. Aislá el punto donde se corta el flujo y hacé el cambio mínimo.

Nivel 2TEST-004Network IDS

Anomalía UDP controlada

Practicá una detección de red end-to-end sin contención automática y sin convertir una anomalía en “DDoS”.

TEST → GW/Suricata SID 1000002 → EVE JSON → Wazuh Rule 86601
0. Objetivo, alcance y precondiciones

Qué entrenás: triage de una alerta NIDS basada en tasa, validando el camino completo sin confundir “match de regla” con “DDoS”.

  • SOC-TEST-01 = 10.77.0.10 y gateway 10.77.0.1.
  • Suricata, Wazuh Agent y nftables activos en SOC-GW-01.
  • UDP/65000 reservado para el harness de laboratorio.
  • Regla SID 1000002 cargada; CHG-025 sigue siendo detection-only.
1. Generar el evento
  1. Desde Windows PowerShell entrá al gateway:
ssh -p 2223 socops@127.0.0.1
  1. Desde SOC-GW-01 entrá al workload:
ssh socops@10.77.0.10
  1. Ejecutá primero el baseline negativo:
hping3 --udp -p 65000 -c 5 -i 1 10.77.0.1
  1. Después ejecutá el caso positivo acotado:
hping3 --udp -p 65000 -c 30 -i u20000 10.77.0.1

No uses --flood. Este caso está diseñado como anomalía de tasa limitada, no como prueba DoS/DDoS.

2. Localizar la alerta y qué deberías ver

Wazuh Dashboard · Threat Hunting

  1. Acotá la ventana al test.
  2. Filtrá preferentemente por data.alert.signature_id:1000002.
  3. Como control adicional usá rule.id:86601 y verificá la firma Suricata en el documento.
  4. Confirmá que el agente sea SOC-GW-01 y la fuente /var/log/suricata/eve.json.
  • Suricata SID 1000002: MINI-SOC Controlled UDP Rate Anomaly.
  • Origen 10.77.0.10 → destino 10.77.0.1:65000/UDP.
  • Acción Suricata: allowed.
  • Wazuh Rule 86601, level 3, desde /var/log/suricata/eve.json.
  • No debe aparecer un nuevo SID 1000001 ni Active Response.
3. Triage SOC L1
  1. En Threat Hunting buscá data.alert.signature_id:1000002 o Rule 86601 y acotá el tiempo.
  2. Validá origen, destino, puerto, protocolo, agente SOC-GW-01 y signature.
  3. Revisá eventos cercanos para descartar que el flujo haya activado SID 1000001 o contención.
  4. Si querés corroborar el evento directamente en GW:
grep -F '"signature_id":1000002' /var/log/suricata/eve.json | tail -n 1
  1. Evaluá impacto real. La condición de tasa por sí sola no prueba ataque ni degradación de servicio.
4. Decisión y cierre

Ejercicio validado: True Positive — Authorized Security Test / Benign.

Escalación: no. Contención: no. Active Response: no. ATT&CK: no forzado sin contexto adversario.

En un caso no autorizado, escalá si

  • la tasa/patrón persiste fuera de la ventana de prueba;
  • el origen o destino no pertenece al harness esperado;
  • hay evidencia de impacto de disponibilidad;
  • aparecen múltiples firmas o activos afectados.

Registro mínimo: timestamp · src/dst/puerto/protocolo · SID 1000002 · Wazuh 86601 · agente · acción allowed · volumen observado · impacto · disposición.

Cierre ejemplo: “TP benigno. Threshold UDP del laboratorio alcanzado y centralizado en Wazuh. Sin impacto, sin Active Response y sin necesidad de contención.”

5. Si la alerta o el resultado no aparece
  • Confirmá que Suricata está activo y que SID 1000002 está cargado.
  • Revisá primero EVE JSON; si el evento existe allí pero no en Wazuh, el problema está aguas abajo del sensor.
  • Confirmá Wazuh Agent de GW activo y que lee /var/log/suricata/eve.json.

Regla de operación: no “arregles” varias capas a la vez. Aislá el punto donde se corta el flujo y hacé el cambio mínimo.

Nivel 3TEST-005Response

Active Response con rollback

Practicá la diferencia entre detectar y contener: aquí sí existe una respuesta automática acotada.

SID 1000001 → Wazuh 86601 → local 100021 → Python → nftables → timeout 60 s
0. Objetivo, alcance y precondiciones

Qué entrenás: verificar no sólo una detección, sino todo el ciclo de contención y recuperación con blast radius limitado.

  • SID 1000001 presente y semánticamente sin cambios.
  • Regla local Wazuh 100021 habilitada.
  • Script mini-soc-nft-block.py disponible con permisos correctos.
  • Allowlist exacta 10.77.0.10 y timeout 60 s.
  • Baseline de conectividad registrado antes de disparar el evento.
1. Generar el evento
  1. Desde SOC-TEST-01, comprobá baseline de salida:
ping -c 3 -W 2 1.1.1.1
  1. Generá un solo Echo Request al gateway:
ping -c 1 10.77.0.1
  1. Esperá aproximadamente 5 segundos.
  2. Volvé a probar conectividad de salida:
ping -c 3 -W 2 1.1.1.1
  1. Esperá ~60 segundos y repetí el ping de salida para comprobar recuperación.
2. Secuencia esperada y puntos de control

Correlación que tenés que comprobar

  1. Suricata genera SID 1000001.
  2. Wazuh lo recibe mediante Rule 86601.
  3. La regla local 100021 acota el trigger.
  4. Active Response ejecuta el script local en GW.
  5. nftables aplica el bloqueo runtime y luego revierte por timeout.
  • Suricata SID 1000001 por ICMP autorizado.
  • Wazuh Rule nativa 86601.
  • Regla local Wazuh 100021 como trigger específico.
  • Active Response local en SOC-GW-01.
  • nftables bloquea temporalmente sólo 10.77.0.10.
  • Después del timeout de 60 s se ejecuta DELETE y vuelve la conectividad.
3. Triage / validación SOC L1
  1. Confirmá que el evento corresponde a SID 1000001, no a 1000002.
  2. Revisá que el origen sea exactamente 10.77.0.10.
  3. En el gateway, verificá el estado runtime de la tabla:
sudo nft list table inet mini_soc_ar
  1. Durante el bloqueo, el set blocked_ipv4 debe contener sólo 10.77.0.10.
  2. Después de ~60 s, verificá que el set quede vacío y que TEST recupere conectividad.
  3. Confirmá salud final:
systemctl is-active wazuh-agent suricata nftables
sysctl net.ipv4.ip_forward
4. Decisión y cierre

Ejercicio validado: True Positive — Authorized Security Test / Benign. La contención automática fue intencional.

Control de seguridad: la respuesta está limitada por regla específica, allowlist exacta, ejecución local, tabla nftables runtime y timeout. No modifica /etc/nftables.conf.

Escalá / detené la prueba si

  • el bloqueo alcanza una IP distinta de 10.77.0.10;
  • la administración o telemetría Wazuh se ve afectada;
  • no ocurre DELETE al finalizar el timeout;
  • la conectividad no se recupera o algún servicio queda degradado.

Registro mínimo: alerta inicial · Rule 100021 · hora ADD · contenido del set · pérdida de conectividad · hora DELETE · recuperación · salud final.

Cierre ejemplo: “TP benigno con respuesta automática autorizada. Contención limitada a TEST, rollback a 60 s y servicios saludables al finalizar.”

5. Si la alerta o el resultado no aparece
  • Confirmá primero que SID 1000001 llegó a Wazuh.
  • Después verificá Rule 100021 y el Active Response; no saltes directamente a nftables.
  • Si existe ADD sin DELETE, priorizá recuperación y revisá el estado runtime antes de repetir la prueba.

Regla de operación: no “arregles” varias capas a la vez. Aislá el punto donde se corta el flujo y hacé el cambio mínimo.

Ficha rápida para cualquier caso: Hora → activo → usuario/IP → regla/SID → fuente del log → eventos relacionados → impacto → autorización → disposición → acción → evidencia de cierre. Si no podés completar uno de esos campos, todavía te falta contexto para cerrar con confianza.
